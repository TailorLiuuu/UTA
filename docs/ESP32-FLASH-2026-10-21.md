# ESP32-S3 云端烧录实测 — 2026-10-21

通过 UTA 将 Mac 上的 ESP32-S3 转发到一台 Linux 测试服务器，直接在服务器的
`/dev/ttyACM0` 上完成固件写入、7 个镜像的独立校验和复位启动验证。
烧录进程和固件都位于服务器。本文为去除私人项目路径和设备身份后的公开记录。

## 测试条件与结果

- 设备：ESP32-S3 QFN56 revision v0.2，16 MB Flash，8 MB PSRAM。
- USB：Espressif `303a:1001`；设备序列号不公开。
- 固件：测试工程的既有构建输出，应用镜像 2,484,256 字节；镜像本身不包含在 UTA 中。
- 工具：esptool 4.12.0，使用 `--no-stub`。
- 从写入开始到独立校验结束共 327 秒。这是该硬件、网络和固件的一次实测，不是速度保证。

## 验证步骤

1. 接入后读取芯片和 Flash ID，核对型号与构建输出。
2. 用 ROM 模式备份前 128 KiB，包含启动区、分区表和 NVS。
3. 根据工程生成的 `flash_args` 写入 7 个镜像，没有执行全片擦除或 eFuse 写入。
4. 单独执行 `verify_flash`，7 个镜像均返回 `verify OK (digest matched)`。
5. 重新读取 NVS `0x9000..0xefff`，24,576 字节与备份逐字节一致。
6. 通过同一云端串口复位并采集启动日志，确认从预期应用分区启动，版本标记与目标构建一致。

约 55 秒的启动日志只观察到一次启动，没有 Guru Meditation、Backtrace 或 assert failed。
这证明烧录与基本启动，不代表音频、NFC、网络等完整产品功能通过验收。
前 128 KiB 备份不是整个旧固件的完整备份。原始日志和设备备份保留于私有测试环境，不随仓库发布。

## 已知限制

默认 stub 模式可以读取芯片信息，但读取 Flash 大块数据时出现
`Corrupt data, expected 0x1000 bytes but received ...`，在 115200 和 460800 下均复现。
根因尚未最终定位，不能声称默认高速模式已验证可靠。

同一链路改用 `--no-stub` 后，128 KiB 读取、完整写入、独立校验和 NVS 读取均成功，
无需修改 UTA 或目标固件。参数和语法应与实际 esptool 版本一致。

复现实验时先用 `uta-server list` 确认当前端口，使用自己工程的镜像、偏移和目标型号。
不要直接复用其他项目的烧录布局。UTA 只负责 USB 传输，不检查这些烧录参数。
